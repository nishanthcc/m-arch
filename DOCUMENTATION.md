## 2. Abstract

Modern software engineering repositories grow rapidly in structural complexity, integrating heterogeneous programming languages, distributed services, third-party libraries, and intricate deployment configurations. Traditional manual peer code reviews are bottlenecked by human cognitive bandwidth, whereas monolithic Large Language Model (LLM) review prompts frequently suffer from context-window truncation, context hallucination, lack of verifiable source citations, and high vulnerability to vendor API throttling.

This project designs and implements **M-ARCH** (Multi-Agent Architecture Review & Code Hygiene), a specialized multi-agent Retrieval-Augmented Generation (RAG) framework tailored for automated static software architecture, security, code quality, dependency supply chain, and documentation reviews. M-ARCH decomposes the holistic repository inspection inquiry across five autonomous specialist agents coordinated by a centralized Lead Orchestrator:
1. `code_agent` (Static code patterns and test suite inventory),
2. `security_agent` (Credential leakage, injection vectors, and CWE/OWASP vulnerability matching),
3. `documentation_agent` (Operational instructions, architectural documentation, and config discrepancy checks),
4. `dependency_agent` (Manifest scanning, lockfile presence, supply chain risks, and license audit), and
5. `evidence_verifier` (An independent pre-synthesis quality gate enforcing empirical citation grounding and filtering ungrounded claims).

Inter-agent collaboration is structured using Google's official **Agent-to-Agent (A2A)** protocol, standardizing task dispatching, context propagation, and artifact exchange. Autonomous tool execution and resource retrieval adhere strictly to the **Model Context Protocol (MCP v2)**, isolating specialist capabilities via role-based tool permission boundaries. To guarantee offline resiliency, cost predictability, and operational privacy, M-ARCH implements an intelligent **Provider Router** supporting Groq cloud acceleration (`openai/gpt-oss-120b`), local Ollama on-device inference (`qwen2.5-coder:7b` / `qwen2.5-coder:3b`), and dynamic Auto-failover with automated secret redaction. Project code ingestion supports public/private GitHub repositories, local ZIP archives, and multi-file directory trees, indexed into an immutable snapshot layer with hybrid vector (384-dimensional dense semantic embeddings) and sparse (SQLite FTS5 BM25) retrieval fused via Reciprocal Rank Fusion (RRF).

Every finding generated by M-ARCH is bound to verifiable source code excerpts, line coordinates, explicit confidence scores, and verification status tags (`static_analysis`, `inference`, `not_tested`), preventing unverified assertions from masquerading as confirmed runtime bugs. Live end-to-end server audits confirm full operational functionality across all core workflows, establishing a grounded, auditable baseline for AI-augmented code governance.

## 4. Introduction

### 4.1 Background and Domain Context
Software quality assurance and security auditing are foundational pillars of reliable software engineering. In contemporary continuous integration and deployment (CI/CD) pipelines, development teams rely heavily on pull request reviews to catch logic defects, maintain architectural conventions, identify dependency risks, and intercept security vulnerabilities prior to production deployment. However, modern software applications frequently span polyglot microservices, deep dependency trees, complex database interaction layers, and cloud infrastructure manifests. Consequently, comprehensive manual code review demands immense human effort, deep multidisciplinary expertise, and substantial time, resulting in delayed release cycles and overlooked vulnerabilities.

Retrieval-Augmented Generation (RAG) has emerged as a promising paradigm to supply generative AI models with private, context-specific knowledge. By indexing repository files and retrieving semantically relevant code snippets at query time, RAG mitigates the factual hallucinations inherent in standard zero-shot LLM queries. However, naive single-prompt RAG architectures exhibit severe limitations when applied to full-repository audits:
1. **Context Smothering & Incoherence:** Passing hundreds of retrieved code snippets into a single monolithic LLM prompt overwhelms the model's attention mechanism, leading to superficial reviews where subtle security or dependency risks are ignored.
2. **Lack of Specialization:** A single general-purpose prompt fails to balance the competing analytical priorities of static code efficiency, test coverage, cryptographic safety, licensing compliance, and deployment documentation.
3. **Unverifiable Assertions:** Generative models often summarize code with convincing but ungrounded claims, citing non-existent files or hallucinating runtime bugs without empirical grounding.
4. **Cloud Vendor Lock-In & Privacy Vulnerabilities:** Relying exclusively on commercial cloud LLM APIs exposes proprietary source code to third-party endpoints and makes pipelines vulnerable to rate limits (HTTP 429) or cloud service outages.

### 4.2 The Emergence of Agentic Systems (A2A & MCP)
To overcome monolithic RAG constraints, modern AI research has shifted toward **Agentic Multi-Agent Systems**. Rather than treating the language model as a passive text generator, agentic systems structure the problem into coordinated, semi-autonomous entities—agents—equipped with distinct operational roles, dedicated prompt specifications, private tool suites, and memory artifacts:
* **Agent-to-Agent (A2A) Protocol:** An open communication standard developed by Google and the wider open-source ecosystem that formalizes how autonomous agents discover one another via standardized Agent Cards, initiate hierarchical or peer-to-peer work orders (`Task`), preserve conversational context (`context_id`), and return structured, versioned data envelopes (`Artifact`).
* **Model Context Protocol (MCP):** An open standard pioneered by Anthropic that standardizes how language model agents connect securely to external data sources, local development tools, and database endpoints through isolated, permission-gated tool definitions.

### 4.3 Motivation for M-ARCH
Developers and engineering leads require an automated, private, and mathematically grounded architectural review assistant that does not merely produce generic text summaries, but delivers **rigorously cited, evidence-backed findings** mapped to physical source lines. M-ARCH was developed to fulfill this need by combining:
1. A multi-tier ingestion engine accepting GitHub repositories, uploaded ZIP archives, and multi-file directory structures;
2. An offline-capable hybrid retrieval pipeline combining dense semantic vector embeddings with SQLite Full-Text Search (FTS5) via Reciprocal Rank Fusion (RRF);
3. A multi-agent specialist architecture communicating via A2A;
4. Isolated tool and data retrieval via MCP with role-based access control;
5. A pre-synthesis Quality Gate agent (`evidence_verifier`) that programmatically inspects candidate claims against retrieved code excerpts before the final report is compiled; and
6. A hybrid cloud/local provider router featuring Groq cloud inference and local Ollama inference with automatic failover and local regex/entropy secret redaction.

## 5. Problem Statement

Modern software engineering lacks an automated, verifiable, and privacy-preserving code review system capable of inspecting full repositories across architecture, security, documentation, and dependencies without succumbing to LLM hallucinations, monolithic context degradation, or cloud API rate-limiting failures.

Existing static analysis tools (e.g., SonarQube, Bandit, ESLint) produce high volumes of rigid, isolated rule warnings without understanding holistic business logic or inter-service architecture. Conversely, commercial generative AI assistants operate primarily as single-turn chat interfaces that lack verifiable citation grounding, provide no standardized agent-to-agent task governance, cannot run reliably offline on local hardware, and fail to distinguish static code observations from verified runtime behavior.

The core challenge addressed by this project is:
> *How to design and implement an end-to-end software review framework that decomposes repository inspection across specialized, role-isolated AI agents using A2A and MCP, grounds all findings in verifiable hybrid-retrieved code evidence, validates assertions via an automated pre-synthesis verification gate, and dynamically routes inference between cloud acceleration (Groq) and local execution (Ollama) with deterministic fallback?*

## 6. Objectives

The primary aim of M-ARCH is to provide a multi-agent, evidence-grounded architectural review and code hygiene system. The specific technical and engineering objectives are:

1. **Multi-Source Code Ingestion & Snapshot Preservation:**
   - Implement ingestion pathways for public/private GitHub repositories (via commit-resolved shallow tarball extraction), local ZIP archives, and multi-file folder uploads preserving directory hierarchies.
   - Establish an immutable snapshot database layer computing cryptographic SHA-256 hashes for repository versions to prevent drift during review execution.
2. **Hybrid RAG Pipeline with Reciprocal Rank Fusion (RRF):**
   - Implement a dense semantic vector indexing service using a lightweight 384-dimensional embedding model (`all-MiniLM-L6-v2`) paired with an offline vector store.
   - Implement a sparse keyword retrieval index using SQLite FTS5 with BM25 ranking.
   - Fuse dense and sparse candidate excerpts using Reciprocal Rank Fusion (RRF, $k=60$) to balance conceptual semantic matching with exact syntax/identifier retrieval.
3. **Multi-Agent Decomposition via Agent-to-Agent (A2A) Protocol:**
   - Construct five specialized agents (`code_agent`, `security_agent`, `documentation_agent`, `dependency_agent`, and `evidence_verifier`) coordinated by an `orchestrator_agent`.
   - Implement official A2A protocol entities (`Task`, `TaskStatus`, `TaskState`, `Artifact`, `AgentCard`) to govern work distribution, context isolation, and structured artifact delivery.
4. **Role-Gated Tool Access via Model Context Protocol (MCP v2):**
   - Expose backend retrieval and inspection functions as standard MCP tools (`list_project_sources`, `search_project_code`, `search_project_documents`, `get_source_excerpt`, `get_dependency_manifest`, `get_test_inventory`, `search_security_knowledge`, `get_review_evidence`, `get_agent_trace`).
   - Enforce strict role-based MCP permissions so that specialist agents can only invoke the tools necessary for their analytical scope.
5. **Quality Gate Evidence Verification & Grounding:**
   - Implement an automated `evidence_verifier` agent that inspects candidate findings, validates that cited line ranges physically exist in the project snapshot, detects ungrounded overstatements, rejects unsupported claims, and calculates a formal `citation_coverage_score`.
6. **Resilient AI Routing & Local Privacy Protection:**
   - Implement an intelligent Provider Router supporting `Groq`, `Ollama`, `Auto` (automatic failover), and `Hybrid` (role-based routing).
   - Integrate pre-flight regex and entropy secret redaction in cloud mode to prevent accidental leakage of API keys, tokens, or credentials to third-party endpoints.
   - Implement automatic retry and graceful fallback to local Ollama (`qwen2.5-coder:7b`) whenever Groq encounters transient HTTP 429 (rate-limiting) or network errors.
7. **Transparent Auditability & Interactive User Experience:**
   - Build a Next.js (React 19) dashboard displaying real-time Server-Sent Events (SSE) review streams, interactive project inventories, agent execution traces, finding evidence drawers with code snippets, security knowledge collection toggles, and Markdown/HTML review export.

## 7. Scope, Constraints, and Limitations

### 7.1 Scope of the System
* **Static Inspection Only:** M-ARCH is strictly a **static analysis and architectural inference framework**. It inspects source code text, configuration files, and dependency manifests. It **does not execute user code**, run dynamic test suites, deploy containers, or perform live network penetration fuzzing.
* **Supported Project Languages:** Ingestion and hybrid chunking support general text, Python, TypeScript, JavaScript, JSON, YAML, Markdown, Shell, Go, Rust, and standard dependency manifests (`package.json`, `requirements.txt`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `pom.xml`).
* **Deployment Model:** M-ARCH runs as a locally hosted full-stack application (FastAPI backend on port 8000, Next.js frontend on port 3000), storing metadata in SQLite and files in local storage.

### 7.2 Hardware and Compute Constraints
* **Local Inference Latency:** Running local LLMs via Ollama (e.g., `qwen2.5-coder:7b`) on commodity developer workstations without dedicated high-end VRAM (e.g., running partially or entirely on CPU) introduces significant inference latency. Generating full structured JSON across large context chunks can take 30 to 180 seconds per agent task.
* **Memory Headroom:** Ingesting large archives (>100MB or >10,000 files) is bounded by workstation RAM and SQLite database write concurrency. Default upload limits are enforced at 100 MB (`UPLOAD_MAX_MB=100`).

### 7.3 Cloud Provider and API Rate Limits
* **Groq Free-Tier Rate Limits:** The Groq cloud endpoint enforces an **8,000 Tokens Per Minute (TPM)** quota and 1,000 Requests Per Day limit on free-tier preview models such as `openai/gpt-oss-120b`. When multi-agent reviews dispatch several large prompts sequentially, the 8,000 TPM limit can be exceeded within a single minute, triggering HTTP 429 exceptions that necessitate retry backoff or fallback to Ollama.
* **Model Availability Drift:** Cloud model IDs evolve frequently. For example, `llama-3.3-70b-versatile` may be restricted or unavailable on certain tier keys, necessitating model fallback configurations (`openai/gpt-oss-120b` or `qwen/qwen3.8-27b`).

### 7.4 Verification and Soundness Boundaries
* **Static Observation vs. Runtime Fact:** Findings labeled `static_analysis` represent patterns physically identified in text. Findings labeled `inference` represent suspected architectural behaviors. An absence of identified vulnerabilities **does not guarantee that the software is secure**, nor does a clean review report certify production readiness.
* **Unsupported Scope:** Private repositories requiring two-factor interactive OAuth authentication that cannot be accessed via standard GitHub personal access tokens are unsupported. Proprietary binary formats, compiled bytecode (`.pyc`, `.class`), and compiled executables are excluded from indexing.

## 9. System Architecture

### 9.1 High-Level Architectural Decomposition
The M-ARCH framework is organized into six interconnected architectural layers:
1. **Presentation Layer (Frontend):** Next.js 15 (React 19) Single Page Application styled with Vanilla CSS tokens, offering real-time Server-Sent Events (SSE) review streams, project creation modals, interactive code inspection drawers, dynamic agent status cards, and settings management.
2. **API & Orchestration Layer (Backend):** FastAPI asynchronous ASGI server providing RESTful endpoints (`/api/v1/*`), background worker execution, and Server-Sent Event streaming.
3. **Storage & Snapshot Layer:** SQLite database accessed asynchronously via SQLAlchemy 2, storing projects, sources, immutable `SourceSnapshot` records, reviews, tasks, findings, and evidence, complemented by SQLite FTS5 for full-text search.
4. **Retrieval & Embedding Engine:** Hybrid retrieval pipeline utilizing local 384-dimensional dense semantic embeddings (`all-MiniLM-L6-v2`) and sparse BM25 FTS5 indexes fused through Reciprocal Rank Fusion (RRF, $k=60$).
5. **Agentic Layer (A2A & MCP):** Lead `OrchestratorAgent` dispatching work to `code_agent`, `security_agent`, `documentation_agent`, `dependency_agent`, and `evidence_verifier` via official A2A `Task` contracts. Tools are executed via the MCP v2 server with strict role-based permission gating.
6. **Provider Routing Layer:** Dual-engine LLM client supporting Groq Cloud acceleration and local Ollama inference with automatic failover, retries, and pre-flight secret redaction.

## 10. Module Description and Data Flow

### 10.1 Module 1: Project Source Ingestion & Snapshotting
* **GitHub Ingestion:** Validates repository URLs (strict HTTPS regex preventing command injection or SSRF), resolves the default branch or ref commit SHA via GitHub API, downloads a lightweight tarball stream, strips the root folder, rejects files exceeding 5MB or binary mime-types, and stores files in `data/storage/{project_id}`.
* **Local ZIP Upload:** Validates ZIP archives against directory traversal attacks (Zip Slip via `is_safe_path`), extracts files safely, preserves relative subdirectory paths, computes per-file SHA-256 hashes, and records a `SourceSnapshot` (`snapshot_type="zip_upload"`).
* **Multi-File & Folder Upload:** Handles multipart `FormData` submissions containing individual files or complete directory trees, preserving `webkitRelativePath` to recreate accurate filesystem hierarchies.
* *Code Paths:* `backend/app/services/ingestion/github_importer.py`, `backend/app/services/ingestion/validator.py`, `backend/app/api/v1/endpoints/sources.py`.

### 10.2 Module 2: Code Extraction, Chunking & Hybrid Indexing
* **Chunking Service:** Iterates across ingested code and documentation files. For code files, it breaks text into logical windows of 60 lines with 10-line overlaps; for markdown documentation, it splits on header boundaries (`#`, `##`, `###`).
* **Dense Semantic Indexing:** Generates 384-dimensional dense vectors using `LocalEmbeddingService` (`all-MiniLM-L6-v2` token frequency and character trigram hashing with L2 normalization), persisting vector matrices in `data/vectors/{project_id}.npz`.
* **Sparse FTS5 Indexing:** Inserts chunk text into a SQLite virtual table (`chunks_fts`) configured with BM25 tokenizers for high-speed keyword matching.
* *Code Paths:* `backend/app/services/ingestion/chunker.py`, `backend/app/services/embeddings/local_embeddings.py`, `backend/app/services/retrieval/fts_index.py`.

### 10.3 Module 3: Hybrid Retrieval with Reciprocal Rank Fusion (RRF)
* Given an agent query $q$, the retriever executes dense cosine similarity over the vector matrix and sparse BM25 query over SQLite FTS5 in parallel.
* Fuses candidate chunk ranks using Reciprocal Rank Fusion:
  $$\text{RRF\_Score}(d) = \sum_{m \in \{\text{dense}, \text{fts}\}} \frac{w_m}{k + \text{rank}_m(d)}$$
  where $k = 60.0$, $w_{\text{dense}} = 0.6$, and $w_{\text{fts}} = 0.4$.
* Ranks chunks descending by $\text{RRF\_Score}$ and returns top-$K$ candidate excerpts with exact start/end line coordinates.
* *Code Paths:* `backend/app/services/retrieval/retriever.py`.

### 10.4 Module 4: Agent-to-Agent (A2A) Coordination
* **Lead Orchestrator:** Instantiates an official A2A `Task` for each active specialist with initial state `TASK_STATE_WORKING`.
* **Specialist Execution:** Each specialist receives its specific prompt contract, executes MCP tools to gather code evidence, and generates candidate findings structured strictly according to the schema.
* **Artifact Delivery:** Upon completion, the specialist wraps findings into an A2A `Artifact` and transitions task state to `TASK_STATE_COMPLETED`.
* *Code Paths:* `backend/app/a2a/protocol.py`, `backend/app/a2a/cards.py`, `backend/app/agents/orchestrator/agent.py`.

### 10.5 Module 5: Model Context Protocol (MCP v2) Tool Execution
* Isolates tool definitions into distinct callable handlers with typed inputs.
* Enforces `ROLE_MCP_PERMISSIONS` mapping:
  - `code_agent`: `list_project_sources`, `search_project_code`, `get_source_excerpt`, `get_dependency_manifest`, `get_test_inventory`.
  - `security_agent`: `list_project_sources`, `search_project_code`, `search_project_documents`, `get_source_excerpt`, `get_dependency_manifest`, `search_security_knowledge`.
  - `documentation_agent`: `list_project_sources`, `search_project_documents`, `get_source_excerpt`.
  - `dependency_agent`: `list_project_sources`, `get_dependency_manifest`, `get_source_excerpt`.
  - `evidence_verifier`: `get_source_excerpt`, `get_review_evidence`.
  - `orchestrator`: `list_project_sources`, `get_review_evidence`, `get_agent_trace`.
* *Code Paths:* `backend/app/mcp/tools.py`, `backend/app/mcp/permissions.py`, `backend/app/mcp/server.py`.

### 10.6 Module 6: Pre-Synthesis Evidence Verification Gate
* Prior to executive synthesis, candidate findings from all specialists are routed to `evidence_verifier`.
* Verifies that each finding cites physical source lines, checks that cited code excerpts match character content in storage, rejects claims with empty or ungrounded evidence, flags overstatements, and computes a system `citation_coverage_score`.
* *Code Paths:* `backend/app/agents/verifier/agent.py`.

### 10.7 Module 7: Provider Router & Secret Redaction
* Dispatches LLM generation requests to Groq Cloud API or local Ollama server based on system configuration (`Auto`, `Groq`, `Ollama`, `Hybrid`).
* Filters all outgoing prompts through `redact_secrets()`, replacing AWS keys, GitHub tokens, Slack keys, and private certificates with `[REDACTED_*]` tokens.
* Detects HTTP 429 rate limits or network drops on primary provider and executes automatic failover to the configured fallback provider.
* *Code Paths:* `backend/app/providers/router.py`, `backend/app/providers/groq.py`, `backend/app/providers/ollama.py`, `backend/app/providers/redaction.py`.

### 10.8 Module 8: Findings, Verification States & Report Export
* Persists verified findings linked to `Evidence` records in SQLite.
* Enforces verification status labels: `static_analysis`, `inference`, `runtime_confirmed`, `manual_review_required`, `not_tested`.
* Generates downloadable, structured Markdown and HTML reports complete with executive summary, categorized findings, line citations, and technical scope limitations.
* *Code Paths:* `backend/app/services/reports/exporter.py`, `backend/app/api/v1/endpoints/reviews.py`.

## 12. Project Sources and Knowledge Sources

### 12.1 Project Sources vs. Conventional ML Datasets
In academic machine learning reports, the term "dataset" typically denotes a collection of labeled training samples (e.g., ImageNet, MNIST, CIFAR). In M-ARCH, **project sources are not machine learning training datasets**. M-ARCH does not train, fine-tune, or modify the weights of any neural network model.

Instead, M-ARCH treats ingested software repositories as **unstructured source text to be retrieved, audited, and reasoned over dynamically** via RAG. Project sources represent target software repositories supplied by developers for inspection via three input channels:
1. Public and private GitHub repositories fetched via HTTPS commit-resolved shallow tarballs;
2. Local ZIP archives uploaded directly from developer workstations; and
3. Multi-file directory trees uploaded via browser multipart `FormData`.

To ensure that specialist agents do not rely solely on memorized LLM weights when auditing security and code quality, M-ARCH integrates versioned, authoritative cybersecurity knowledge collections managed by `KnowledgeManager`:

## 13. Methodology

The step-by-step working procedure of the M-ARCH framework follows an eight-stage sequential pipeline:

```
[User Ingestion] -> [Snapshot Hashing] -> [Hybrid Indexing] -> [Review Request] 
      -> [A2A Decomposition] -> [MCP Tool Execution] -> [Evidence Verification] -> [Executive Synthesis]
```

### 13.1 Step 1: Secure Ingestion and Snapshotting
1. The user supplies a GitHub URL or uploads a local archive/files via the `/projects` interface.
2. Ingestion validators verify file size (<5MB per file, <100MB aggregate) and ensure path safety (`is_safe_path` prevents traversal escapes).
3. The server extracts files to `data/storage/{project_id}`, computes individual SHA-256 content hashes, and creates an immutable `SourceSnapshot` record with an aggregate snapshot hash.

### 13.2 Step 2: Content Chunking and Hybrid Indexing
1. Text files are parsed and segmented into overlapping windows (60 lines with 10-line overlap for code; markdown headers for documentation).
2. Each chunk receives a deterministic unique ID: `chunk_{source_id}_{index}`.
3. Chunks are embedded into 384-dimensional dense vectors using `LocalEmbeddingService` and stored in `data/vectors/{project_id}.npz`.
4. Simultaneously, chunk text is indexed into SQLite `chunks_fts` for BM25 keyword retrieval.
5. The project status transitions from `indexing` to `ready`.

### 13.3 Step 3: Review Initiation & Inquiry Scope
1. The user creates a review on `/reviews`, specifying the inquiry question (e.g., *"Audit authentication, security vulnerabilities, and deployment readiness"*) and analysis scope (`full`, `security_only`, `code_only`, `architecture`, `docs_only`).
2. An initial `Review` record is created with status `running`.

### 13.4 Step 4: A2A Task Decomposition
1. The Lead `OrchestratorAgent` parses the review scope and determines the required active specialist agents.
2. For each active specialist, the orchestrator constructs an official A2A `Task` (`create_a2a_task`), assigning a unique `task_id` and binding the shared `context_id` (the `review_id`).
3. An `AgentTask` record is persisted in SQLite with status `running`.

### 13.5 Step 5: Specialist MCP Tool Retrieval & Prompt Execution
1. Each specialist agent loads its versioned prompt specification from the Prompt Registry (`backend/app/prompts/registry.py`).
2. The agent executes permitted MCP tools (e.g., `search_project_code`, `search_security_knowledge`, `get_dependency_manifest`) to retrieve grounded evidence.
3. Retrieved code excerpts, security standards, and file inventories are assembled into the agent's prompt context.
4. The prompt is dispatched through the Provider Router:
   - In cloud mode (`Groq`), the text is filtered by `redact_secrets()`. If Groq responds with HTTP 429, the router catches the exception and falls back to local Ollama.
   - In local mode (`Ollama`), inference executes directly on the workstation daemon.
5. The agent returns a strictly formatted JSON object containing candidate findings with line numbers and supporting evidence excerpts.

### 13.6 Step 6: Evidence Verification Gate (`evidence_verifier`)
1. All candidate findings from specialists are passed into the `evidence_verifier` quality gate before synthesis.
2. The verifier audits every candidate finding:
   - Verifies that cited file paths physically exist in the project snapshot;
   - Checks that line start/end numbers correspond to authentic code;
   - Discards claims lacking supporting code evidence;
   - Downgrades confidence or flags overstatements where claims exceed the static text; and
   - Detects contradictions or disagreements between agents.
3. Computes the formal `citation_coverage_score` and packages approved findings into verified A2A artifacts.

### 13.7 Step 7: Executive Synthesis
1. The Lead `OrchestratorAgent` takes verified findings, conflict reports, and agent traces, applying prompt `orchestrator_synthesis_v1_1`.
2. Generates an executive Markdown summary and explicit Technical Scope Limitations section.
3. Persists verified findings, evidence items, and audit events to SQLite.
4. The review status updates to `completed` (or `partial` if non-critical tasks encountered isolated errors).

### 13.8 Step 8: Dashboard Delivery & Report Export
1. Real-time review completion events are published to connected clients via Server-Sent Events (`ReviewEvent`).
2. The dashboard updates to display findings grouped by severity, interactive code snippet drawers, and export actions for Markdown and HTML reports.

*Implementation Evidence: `backend/app/agents/orchestrator/agent.py`, `backend/app/services/reports/exporter.py`.*

## 14. A2A and MCP Design

### 14.1 Demystifying A2A (Agent-to-Agent)
A common misconception in multi-agent AI literature is that "multi-agent" refers to competing foundation models (e.g., pitting GPT-4 against Claude). In M-ARCH, **Agent-to-Agent (A2A) is a formal protocol for inter-agent communication, workflow coordination, and artifact governance**, regardless of which underlying model powers an individual agent.

M-ARCH adopts Google's official A2A standard via the `a2a` Python SDK (`a2a.types`), structuring coordination around three core primitives:
1. **Agent Card (`AgentCard`):** A machine-readable declaration of an agent's identity, role, description, version (`1.1.0`), communication modes, and advertised skill sets (`AgentSkill`). Every M-ARCH agent publishes an official card accessible via `/api/v1/agents/{agent_id}/card`.
2. **A2A Task (`Task`):** An explicit, trackable work assignment. Contains a unique `task_id`, a shared `context_id` (unifying all sub-tasks under a single review), a lifecycle state (`TASK_STATE_WORKING`, `TASK_STATE_COMPLETED`, `TASK_STATE_FAILED`), and conversation history (`Message`).
3. **A2A Artifact (`Artifact`):** A typed, structured data payload generated upon task completion. Specialist findings and evidence collections are packaged into JSON artifacts attached to the completed task, preventing unstructured conversational drift.

```python
# A2A Task Initialization in M-ARCH
a2a_task = create_a2a_task(
    task_id=f"task_{review_id}_{agent.agent_id}",
    context_id=review_id,
    instruction=f"Perform specialist review on project {project_id} addressing: {question}",
    metadata={"agent_id": agent.agent_id, "project_id": project_id}
)
```

### 14.2 Demystifying MCP (Model Context Protocol)
The **Model Context Protocol (MCP v2)** standardizes how language model agents interact with tools, resources, and prompt templates. In M-ARCH, agents never execute raw operating system commands, arbitrary Python scripts, or unvetted database queries. Instead, all data retrieval is encapsulated behind MCP tools exposed through `backend/app/mcp/tools.py`.

To prevent privilege escalation or analytical confusion, M-ARCH implements **Role-Based Tool Gating** (`ROLE_MCP_PERMISSIONS` in `backend/app/mcp/permissions.py`). For instance:
* `code_agent` can inspect code and test inventories, but cannot query security CWE collections;
* `security_agent` can search security knowledge and code, but cannot access agent execution traces;
* `evidence_verifier` cannot search external knowledge, restricting its focus strictly to auditing retrieved snapshot excerpts and review evidence.

```python
# MCP Role-Based Permission Enforcement
def is_tool_allowed_for_agent(agent_id: str, tool_name: str) -> bool:
    allowed = ROLE_MCP_PERMISSIONS.get(agent_id, set())
    return tool_name in allowed
```

### 15.1 Confirmed Models and Hardware Setup
M-ARCH integrates two complementary AI inference tiers:
1. **Cloud Inference Tier (Groq Cloud):**
   - Active Model: `openai/gpt-oss-120b` (confirmed via live Groq API diagnostics).
   - Alternative Models: `openai/gpt-oss-20b`, `qwen/qwen3.8-27b`.
   - Measured Latency: ~300ms to 600ms per agent task completion.
   - Endpoint: `https://api.groq.com/openai/v1/chat/completions`.
   - Credential Config: Configured locally in `backend/.env` via `GROQ_API_KEY`.
2. **Local Inference Tier (Ollama Daemon):**
   - Active Model: `qwen2.5-coder:7b` (primary 7.6B parameter coding model, Q4_K_M quantization, 4.68 GB size).
   - Alternative Models: `qwen2.5-coder:3b` (3.1B params, 1.93 GB size), `qwen2.5-coder:1.5b` (1.5B params, 986 MB size).
   - Measured Latency: ~360ms for health pings; 5s to 30s for short inferences; up to 120s for full multi-thousand token chunk reviews on CPU/shared memory.
   - Endpoint: `http://localhost:11434/api/chat`.

### 15.2 Provider Routing Modes
The system router (`ModelRouter` in `backend/app/providers/router.py`) supports four operational modes:
* **Auto Mode (Default):** Dispatches requests to the primary provider (`Groq`). If Groq encounters HTTP 429 (rate-limiting), connection timeouts, or service errors, it automatically fails over to the fallback provider (`Ollama`) and marks `fallback_used = True`.
* **Groq Mode:** Routes exclusively to Groq Cloud. Raises an error if `GROQ_API_KEY` is missing.
* **Ollama Mode:** Routes exclusively to local Ollama, ensuring 100% air-gapped data isolation.
* **Hybrid Mode:** Routes tasks dynamically based on agent analytical role:
  - `orchestrator` $\rightarrow$ Groq (complex reasoning and synthesis),
  - `code_agent` $\rightarrow$ Ollama (high-volume code token parsing),
  - `security_agent` $\rightarrow$ Groq (knowledge pattern evaluation),
  - `documentation_agent` $\rightarrow$ Ollama (document summarization).

### 15.3 Privacy Protection & Secret Redaction
Before any prompt payload is transmitted to the Groq Cloud API, M-ARCH executes `redact_secrets()`, scanning the text with pre-compiled regular expressions for:
* Generic API keys, tokens, bearer strings;
* AWS Access Key IDs (`AKIA...`) and AWS Secret Access Keys;
* GitHub personal access tokens (`ghp_...`, `gho_...`);
* Slack tokens (`xoxb-...`);
* Private RSA/EC key blocks (`-----BEGIN PRIVATE KEY-----`);
* Passwords embedded in URI connection strings; and
* Groq API keys (`gsk_...`).

### 16.4 Dual-Mode Persona Architecture & Quantitative Granular Scoring (Release v1.3.0)

1. **Technical Review Mode (`technical_review`):**

2. **Simplified Version Mode (`simplified_version`):**
   * **Audience:** Project Managers, Business Executives, and Non-Technical Stakeholders.
   * **Focus:** Real-world impact of the defect and conceptual solution mechanics.
   * **Structure:** `What is the problem?` -> `Why does it matter?` -> `How do we fix it?`.
   * **Strict Prohibitions:** Specific file paths, line numbers, code snippets, and architectural jargon (e.g., "AST parsing", "sanitization", "dependency injection") are strictly forbidden. Simple everyday analogies are utilized.

3. **Quantitative Granular Scoring & SVG Radar Charting:**

     - `performance_score` ($1-10$)

     - `overall_architecture_score` ($1-10$)

## 18. Evaluation Metrics

M-ARCH defines eight concrete, measurable evaluation metrics implemented in `backend/app/api/v1/endpoints/evaluations.py`:

1. **Citation Coverage ($\%$):**
   $$\text{Citation Coverage} = \frac{\sum_{r \in R} \text{score}_{\text{citation}}(r)}{|R|} \times 100$$
   Measures the percentage of reported findings that contain valid, non-empty supporting evidence citations linked to actual source files in the project snapshot.
2. **Citation Correctness ($\%$):**
   $$\text{Citation Correctness} = \left( 1 - \frac{\text{Unsupported Claims}}{\text{Unsupported Claims} + \text{Total Verified Findings}} \right) \times 100$$
   Quantifies the proportion of candidate findings whose cited line numbers and text excerpts accurately match physical repository contents without factual hallucination.
3. **Unsupported Claim Count:** Total number of candidate claims generated by specialist LLM prompts that were detected and rejected by the `evidence_verifier` quality gate due to missing or fabricated citations.
4. **Agent Task Completion Rate ($\%$):** Percentage of dispatched A2A specialist tasks that completed successfully with valid JSON artifacts without encountering fatal unhandled exceptions.
5. **Partial Failure Recovery Rate ($\%$):** Proportion of reviews where one or more specialist tasks failed (e.g., due to rate limits or timeouts) but the Orchestrator successfully synthesized a partial review rather than crashing the overall review.
6. **Provider Fallback Rate ($\%$):** Percentage of review tasks where primary cloud inference encountered an error (such as HTTP 429) and successfully failed over to local Ollama inference.
7. **Import Success Rate ($\%$):** Percentage of repository import jobs (GitHub, ZIP, files) that successfully validated, extracted, and indexed without archive corruption or path traversal errors.
8. **Average Review Duration (Seconds):** Total wall-clock execution elapsed time from review dispatch to final report persistence.

*Implementation Evidence: `backend/app/api/v1/endpoints/evaluations.py:15-100`.*

The M-ARCH project successfully designs, implements, and verifies an end-to-end multi-agent Retrieval-Augmented Generation (RAG) framework for automated software project reviews. By decomposing repository inspection into five specialist agents (`code_agent`, `security_agent`, `documentation_agent`, `dependency_agent`, and `evidence_verifier`) coordinated by an `orchestrator_agent`, the framework overcomes the attention degradation, context truncation, and generalization flaws inherent in monolithic LLM prompts.

Key achievements confirmed by the project implementation include:
1. Standardized agent interoperability using the official Google **Agent-to-Agent (A2A)** protocol, ensuring structured task lifecycles, context preservation, and immutable artifact delivery;
2. Strict isolation of tool capabilities via the **Model Context Protocol (MCP v2)**, enforcing role-based permissions over repository search, AST inspection, and security knowledge retrieval;
3. Mathematically grounded hybrid retrieval combining 384-dimensional dense semantic vectors with SQLite FTS5 BM25 search via Reciprocal Rank Fusion (RRF, $k=60$);
4. An automated **Evidence Verification Gate** (`evidence_verifier`) that programmatically eliminates ungrounded claims and computes formal citation coverage scores prior to report synthesis; and
5. An intelligent **Provider Router** that balances cloud speed (`Groq`) with local on-device privacy (`Ollama`), backed by automated regex/entropy secret redaction and deterministic failover.

M-ARCH demonstrates that AI-augmented code review can be made verifiable, transparent, and resilient without sacrificing developer privacy or relying blindly on ungrounded generative summaries.

## 21. Future Enhancements

While M-ARCH achieves verified static review capabilities, several engineering extensions are planned for subsequent development phases:

1. **Abstract Syntax Tree (AST) & Call-Graph Integration:** Replace sliding-window line chunking with tree-sitter AST parsing to extract full semantic symbol call-graphs, enabling cross-file taint analysis.
2. **Interactive Pull Request Webhooks (GitHub App):** Extend the GitHub ingestion service into a bidirectional GitHub App that automatically triggers M-ARCH reviews upon pull request creation and posts inline review comments citing verified line numbers.
3. **Automated Remediation Patch Generation:** Introduce an optional code-patching agent that generates syntactically valid Git diffs (`.patch` files) for verified findings, allowing developers to apply one-click remediations.
4. **Enhanced Provider Model Support:** Integrate support for Google Gemini API (`gemini-2.0-flash`) and Anthropic Claude APIs via standard adapter interfaces alongside Groq and Ollama.
5. **Streaming Agent Thought Chains:** Expand the frontend Server-Sent Events listener to stream real-time reasoning thoughts from individual specialist agents as they formulate hypotheses.

### 23.3 Specialized Agent Registry
Defined in `backend/app/a2a/cards.py`:

1. **`orchestrator` (M-ARCH Lead Orchestrator):** Prompt `orchestrator_synthesis_v1_1`, version `1.1.0`. Decomposes inquiries, coordinates A2A specialists, and synthesizes executive reports.
2. **`code_agent` (Code and Testing Specialist):** Prompt `code_specialist_v1_1`, version `1.1.0`. Analyzes code structure, logic patterns, dependency manifests, and test suite presence.
3. **`security_agent` (Security & Vulnerability Specialist):** Prompt `security_specialist_v1_1`, version `1.1.0`. Scans for hardcoded credentials, injection vectors, and CWE/OWASP violations.
4. **`documentation_agent` (Documentation & Deployment Specialist):** Prompt `documentation_specialist_v1_1`, version `1.1.0`. Audits READMEs, operational instructions, and configuration discrepancies.
5. **`dependency_agent` (Dependency & Supply Chain Specialist):** Prompt `dependency_specialist_v1_1`, version `1.1.0`. Checks package manifests, lockfiles, unpinned versions, and license declarations.
6. **`evidence_verifier` (Evidence & Citation Verifier):** Prompt `evidence_verifier_v1_1`, version `1.1.0`. Pre-synthesis quality gate validating citations, detecting overstatements, and calculating coverage scores.
